1Ringkasan

Marketing Feed adalah feed konten di Home aplikasi sales. Moderator (Tim Marketing) membuat post, poll, dan link sosmed dari Admin Web atau app. Konten bisa langsung tayang, dijadwalkan, atau disimpan sebagai draft. Sales mengirim momen lewat "Bagikan Momen"; kiriman itu bisa disimpan dulu sebagai draft pribadi, lalu masuk antrean review sebelum tayang. Seperti di TikTok, sales juga bisa menyematkan maks. 3 kiriman yang sudah tayang di profilnya (Kiriman Saya).

Tabel dan endpoint-nya belum ada. App masih memakai MarketingFeedDummyDataSource.

2ERD ringkas

Gambaran besar: hanya nama tabel dan relasinya, dibaca dari kiri ke kanan. Kolom lengkap setiap tabel ada di ERD detail. Klik nama tabel untuk melihat di mana tabel itu dipakai di prototype.

  • biru = tabel baru, abu-abu = tabel existing (sudah ada di backend).
  • Teks kecil abu-abu di samping tabel = isi penting tabel itu, mis. tempat thumbnail link dan kolom sematan. Kolom lengkap ada di ERD detail.
  • A ──1:N── B artinya 1 baris A punya banyak baris B, dan B menyimpan id A sebagai FK. 1:1 artinya 1 baris A punya paling banyak 1 baris B.
  • Garis putus-putus = hubungan tanpa FK. Di sini hanya notifikasi, yang menunjuk post lewat link_url.
  • app_m_user juga dirujuk lewat user_id oleh t_feed_poll_vote, t_feed_reaction, t_feed_comment, dan t_feed_comment_like, serta lewat pin_user_id dan review_user_id oleh t_feed_post. Garisnya tidak digambar supaya diagram tetap sederhana; kolomnya ada di ERD detail.

Alur dari sisi pengguna. Bentuk silinder adalah tabel yang ditulis atau dibaca di langkah itu; garis putus-putus berarti update counter. Pakai tombol − / + untuk memperbesar diagram.

4Cara membaca ERD detail

Setiap kotak adalah satu tabel. Contoh kecil di bawah diambil dari ERD detail; angka di kanan menunjuk ke penjelasan di bawahnya.

  1. Nama tabel dan operasinya. [C/R/U/D] artinya fitur Marketing Feed melakukan Create (insert), Read, Update, dan Delete di tabel ini. Tabel existing biasanya cuma [R].
  2. Kolom. Satu baris = satu kolom, seperti tabel di draw.io. Kiri: PK (kunci utama) atau FK (menyimpan id dari tabel lain). Tengah: nama kolom. Kanan: keterangan isinya.
  3. Index dan catatan. Bagian bawah kotak, setelah garis pemisah, berisi INDEX, UNIQUE, dan aturan khusus tabel itu.
  4. Relasi. 1:N artinya 1 baris t_feed_post punya banyak baris t_feed_comment. Dua baris teks di sebelahnya adalah kolom penghubungnya, sama seperti JOIN ... ON t_feed_post.feed_post_id = t_feed_comment.feed_post_id. N:1 kebalikannya (banyak baris menunjuk ke 1 baris), 1:1 artinya berpasangan satu-satu.
  5. Tabel anak digambar menjorok di bawah tabel induknya. Garis │ di kiri menyambungkan semua anak dari induk yang sama.
C R U D
Create (insert), Read (baca), Update (ubah), Delete (hapus). Dipakai juga di bagian "Dipakai di mana".
(existing)
Tabel sudah ada di database utama, hanya direferensikan.
(pd_common)
Tabel ada di database pd_common (diakses lewat db_pd_common()). FK-nya FK logis, tidak dibuat constraint.

Setiap kali status berubah ke published, publish_at diisi waktu saat itu, kecuali post yang tayang dari jadwal: itu memakai waktu jadwalnya.

Sematan profil (profile_pin_at) juga bukan status, dan hanya dihitung selama status published.

8Aturan bisnis

  • Scheduler jalan tiap menit: status = 'scheduled' AND publish_at <= NOW() diubah ke published, lalu insert ke t_global_notifications dan kirim push.
  • Visibilitas feed: status = 'published' AND deleted_at IS NULL AND (project_id IS NULL OR project_id IN <project user>), urut publish_at DESC. Di halaman 1, kiriman milik user sendiri yang berstatus review/rejected ditaruh paling atas, lalu konten yang disematkan, baru feed biasa.
  • Sematan (pin): hanya konten published. Konten dianggap disematkan kalau pinned_at terisi dan (pin_until NULL atau masih di masa depan). Maksimal 3 sekaligus, dicek di backend saat menyematkan (bukan constraint DB). Di app, konten yang disematkan diambil dengan query terpisah (status = 'published' AND pinned_at IS NOT NULL AND (pin_until IS NULL OR pin_until > NOW()), urut pinned_at DESC) dan hanya di halaman 1; query feed biasa mengecualikannya supaya tidak muncul dua kali.
  • Lepas sematan terjadi saat moderator menekan Lepas sematan, konten ditarik ke draft atau dihapus, atau scheduler menemukan pin_until <= NOW(). Ketiganya mengosongkan pinned_at, pin_user_id, dan pin_until.
  • Draft sales: Bagikan Momen bisa disimpan sebagai status = 'draft' (source mobile). Draft hanya terlihat oleh pembuatnya (Kiriman Saya › Draft): tidak masuk feed dan tidak tampil di Admin Web maupun di Draft & Terjadwal moderator. Kirim untuk ditinjau mengubahnya ke review. Admin Web tidak menyediakan "Tarik ke draft" untuk kiriman sales, supaya draft sales selalu milik pembuatnya.
  • Kiriman ditolak: hanya terlihat oleh pengirimnya. Di Kiriman Saya kiriman ini ditampung di folder Ditolak (terpisah dari grid, seperti folder Draft) bersama alasannya. Pengirim bisa memperbaiki lalu mengirim ulang (rejected → review, alasan dan data review lama dikosongkan), memindahkannya ke draft, atau menghapusnya. Selama belum diperbaiki, kiriman tetap tampil di atas feed pengirim sesuai aturan visibilitas feed.
  • Sematan profil (seperti TikTok): sales bisa menyematkan maks. 3 kiriman miliknya yang published lewat profile_pin_at. Di profilnya (Kiriman Saya, atau profil yang dibuka dari feed), kiriman itu tampil paling depan, urut profile_pin_at DESC, lalu sisanya publish_at DESC. Batas 3 dicek di backend. Urutan feed tidak berubah; sematan di atas feed tetap memakai pinned_at dari moderator. Orang lain hanya melihat kiriman published.
  • Edit post yang sudah tayang langsung berlaku di app. post_type tidak boleh diganti.
  • Pengaturan interaksi divalidasi di backend, bukan cuma di UI. Komentar butuh allow_comment = 1; balasan butuh allow_comment = 1 dan allow_reply = 1. Like/dislike ditolak kalau allow_like/allow_dislike = 0.
  • Balasan komentar maksimal 1 tingkat: parent_comment_id harus menunjuk komentar yang parent_comment_id-nya NULL.
  • Vote poll final, tidak bisa diubah. Untuk poll pilihan tunggal (is_multiple = 0), maksimal 1 baris per (feed_post_id, user_id).
  • Reaksi: 1 baris per user per post. Ganti like ↔ dislike = update; batal = delete.
  • Counter (like_count, dislike_count, comment_count, vote_count, total_voters, like_count komentar) diupdate dalam transaksi yang sama dengan insert/delete interaksinya.
  • Media: maksimal 10 file per post (JPG/PNG/MP4, maks 20 MB per file). Poll dan link maks. 1 file (gambar pertanyaan / thumbnail). Lokasi penyimpanan file belum ditentukan (bukan Google Drive, menyusul); file_path menyimpan path/key file di storage itu. Apa pun storage-nya, URL video harus mendukung header Range karena pemutar video iOS butuh byte-range.
  • Media Wall of Fame: foto JPG/PNG atau video MP4 khusus juara #1, disimpan di d_feed_fame_media. Kolomnya sama persis dengan d_feed_post_media, jadi upload dan validasinya (maks. 20 MB) memakai kode yang sama. Sekarang maks. 1 file per juara; kalau nanti mau carousel, cukup naikkan batasnya tanpa ubah tabel. Belum ada media = kartu memakai foto profil (app_m_user.photo), lalu inisial kalau foto profil juga kosong. Video diputar otomatis tanpa suara dan berulang. Kalau job bulanan menghitung ulang peringkat dan juara #1 berganti orang, baris medianya dihapus.
  • Moderator ditentukan lewat permission yang sudah ada (mis. marketing-feed.moderate), bukan kolom baru.

9Konvensi kolom

  • Kolom audit mengikuti tabel existing (m_contacts): create_user_id, update_user_id, created_at, updated_at, dan deleted_at untuk tabel yang memakai soft delete (t_feed_post, t_feed_comment).
  • Nama index: idx_<tabel>_<tujuan>. Nama unique: uq_<tabel>. Nama FK mengikuti Laravel: <tabel>_<kolom>_foreign.
  • Query CREATE TABLE semua tabel baru ada di docs/marketing-feed-schema.sql (sudah diuji di MySQL 8.4).
  • Kolom bernama ranking, bukan rank, karena RANK adalah reserved word di MySQL 8.

  2. Target project: cukup satu project atau semua? Kalau butuh beberapa project sekaligus, project_id diganti tabel pivot d_feed_post_project.
  3. Edit opsi poll setelah ada suara: prototype mempertahankan suara selama jumlah opsinya sama. Ini berisiko kalau teks opsinya diganti. Usulan: opsi dikunci begitu ada suara.
  4. pillar: ada di data prototype tapi tidak ada UI untuk memilihnya. Dipakai untuk laporan atau dibuang?
  5. Platform link: Flutter saat ini hanya mengenal youtube/web, sedangkan prototype punya blog. Enum backend dan app perlu disamakan.
  6. Progress Kamu: pemetaan m_prospect_status ke 5 tahap funnel, dan periode hitungnya (kontak dibuat bulan ini, atau status berubah bulan ini), perlu dikonfirmasi.
  7. Sematan per project: sekarang sematan mengikuti target post (project_id), dan batas 3 dihitung global. Kalau post "Semua project" perlu disematkan di satu project saja, atau batasnya per project, kolom pin dipindah ke tabel t_feed_pin (feed_post_id, project_id, pinned_at, pin_user_id, pin_until).
  8. Umur draft sales: disimpan sampai dihapus sendiri seperti TikTok, atau dihapus otomatis setelah sekian hari (mis. 30 hari) supaya media di storage tidak menumpuk?
  9. Storage media: foto/video feed dan Wall of Fame tidak disimpan di Google Drive. Storage penggantinya (dan cara membentuk URL dari file_path) masih menyusul.
